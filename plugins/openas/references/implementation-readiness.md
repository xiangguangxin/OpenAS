# 设计粒度与实施就绪

设计应使实现者能拆出任务、明确正确行为及验证方法，无需自行补决定产品范围、跨模块接口或数据安全的关键决策。提前确定高代价、跨边界的决定，局部且可逆的实现选择留给 developer；文档页数、文件数量和伪代码行数不作为就绪依据。

## 按风险选择深度

| 变更 | 足够的设计内容 |
| --- | --- |
| 文案、格式、简单配置 | 目标、修改范围、检查方式 |
| 局部功能或明确的缺陷修复 | 当前与预期行为、修改入口、边界、回归场景 |
| 跨模块功能 | 模块职责、接口契约、数据流、错误处理、任务依赖 |
| 并发、持久化、协议或迁移 | 在相关边界补充状态转换、不变量、顺序约束、重试与幂等、失败恢复、兼容和定向验证 |

不机械要求所有项目填写所有栏目。模块内私有函数名、循环组织及符合现有模式的局部拆分通常交给开发者。若选择影响公共接口、数据语义或资源生命周期，则应在设计中明确。

## 必须消除的歧义

需求描述要能转成具体输入、操作与预期结果，并保留非目标。模块边界写清相关输入输出、单位、错误、数据或资源归属；涉及状态时说明正常完成与失败后的可观察状态。

例如“支持大文件上传，做好异常处理”不足以实施。应确认文件大小限制的配置来源、身份要求、文件 ID 与同名策略、成功返回、超限及写入失败行为、失败清理，以及是否排除分片和断点续传。如果文件系统和数据库共同更新，还需明确更新顺序与部分失败后的恢复；不涉及这些机制时无需补造设计。

## 可执行任务

以一个可验证的行为或内聚变更为任务单位，不按固定行数、时长或文件数拆分。“实现后端”通常过大，单独指定每个辅助函数通常过细。任务至少保留：

- 原始需求或验收引用、目标行为与本次非目标。
- 上游输入、依赖及开始条件。
- 允许修改的文件或模块；新项目可给拟议位置，不能伪称路径已存在。
- 交付物、必须遵守的接口和边界，以及可由 developer 决定的细节。
- 能证明完成的场景、检查入口或验证方法，及未具备的环境条件。

例如“实现上传大小限制与失败清理”：沿用已确定的上传入口和存储契约，覆盖正常、超限、写入失败及临时产物清理，交付实现与回归证据。共享文件或依赖未完成的任务不能仅因拆开而并行。

## 就绪判定与未知项

就绪需要同时满足：

- 不存在会改变产品范围、公共接口、持久数据含义或核心正确性的阻断未决项。
- 每项关键验收均映射到现有或拟议的实现模块，以及可执行的验证方法。
- 本次可开始的任务具备所需输入与依赖，验证所需环境可用，或其缺口不阻断当前明确限定的阶段。

将未知项按影响处理：局部、可逆且不改变契约的选择交给 developer；可能推翻架构可行性的未知先形成 research 或 PoC 任务，写清假设、实验、通过标准与停止条件；确需用户决定的产品范围或不可逆取舍才回交用户。研究任务就绪不代表对应产品实现已就绪。

评审时依据现有文档复述实现路径、边界和验收：若合理的独立实现仍可能产生互不兼容的接口或相反的失败行为，指出具体歧义；不能以“写得不够详细”为由笼统阻断。无需为此实际启动多个 agent。

结论用自然语言明确“就绪”“限定范围就绪”或“不就绪”，列出可开始范围、阻断项及关闭证据。沿用宿主已有报告字段与 verdict，不另造不兼容协议。就绪是可进入实施的技术结论，不代替用户授权，也不代表测试已通过。

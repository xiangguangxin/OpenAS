# 验证前置

中文 | [English](verification-first.en.md)

适用于故障修复、行为变更、架构收敛与发布验收。按任务风险选择证据和执行入口，沿用[共享证据规则](evidence-policy.md)及现有授权。

## §0 以有效契约约束实现

先定位已生效的需求、设计和测试判据。实现偏离有效契约时，修对应实现。契约缺失、冲突或被证据推翻时，把偏差回交给上游，在已授权范围内先纠正设计与测试判据再改代码。把“文档要求但实现缺失”和“实现引入未经约定的行为”同时纳入评审。临时实验只用于验证假设，保留业务断言和测试语义。

在改动前取得足以区分故障和环境问题的基线。在确认修复前，以能运行目标对象的检查验证当前版本，记录预期、实际与仍缺少的观测。纯文档与静态约束沿用对应证据。

## CC-A 到 CC-Q

| 条款 | 在 OpenAS 中如何执行 |
| --- | --- |
| CC-A | 先审设计和测试判据，再沿数据流找最后正确、首个异常的边界。同一区域反复失败时重新审合同、所有权和时序。用下方矩阵复核归因。 |
| CC-B | 把任务中声称的根因列为待验证假设，运行能区分候选原因的最小实验。 |
| CC-C | 将模型和工具的状态回报与对象级观测分开。退出码、目标执行、业务断言和产物状态各按所需证据核对。 |
| CC-D | 前提未复现时停止依赖该前提的修改，并回交当前证据和需要修订的输入。可以继续只读调查。 |
| CC-E | 发布修复在隔离环境构建或安装实际候选包。若项目用 overlay 交付，把候选包覆盖到支持的基线，再运行目标回归。 |
| CC-F | 修改前列一份最小文档地图，定位权威需求、设计、测试与接口说明，标出版本、冲突和缺口。 |
| CC-G | 记录基线分支与提交并走项目的 PR/MR 流程。任务包含合并时，读回目标分支和其验证状态后再报告完成。 |
| CC-H | 日志、栈和检查报告使用可定位位置。源码可用 `文件:函数:行号`，运行记录补版本、命令、目标与相关标识。 |
| CC-I | 给实际执行者和验收者传递有效契约、失败基线、验收条件、禁止绕开的约束及证据位置。依据宿主实际能力交接。 |
| CC-J | 路径、环境和业务输入走正常参数、配置或夹具。代码保留生产调用路径，禁止按本机路径或固定测试输入特判。 |
| CC-K | 提交说明写变更动因、契约或根因、相关检查及证据。PR/MR 标明待验和部署限制。 |
| CC-L | 将捕获问题的本地回归纳入适用的现有门禁。外部依赖或长时测试使用明确登记的独立验证入口。 |
| CC-M | 优先保留可维护的结构化观测，包括阶段、对象、关键信号和错误。临时诊断完成后清理或转成受控日志。 |
| CC-N | 接入成果时就验证门禁和责任范围。跳过须标明条件、理由和影响，汇总结果单列跳过。 |
| CC-O | 每个影响判断的结论附可复核证据及强度。标明实测、模拟、静态、推断或未验证。 |
| CC-P | 工具须在本次环境下观测到对应对象与性质。目标未执行、工具加载错对象或模拟环境不具备待测属性时，修正检查或标记缺口。 |
| CC-Q | 让位、单源化或架构收敛同时检查受益路径和让位路径。核对调用者兼容、行为保持和需要的回退。 |

## 二维归因与文档复核

采用项目自己的名称，区分用例、测试平台和被测对象（DUT）。对可能的单元格记录来源、版本及可区分实验。

| 对象 | 方案与判据 | 实现与执行 | 文档与版本 |
| --- | --- | --- | --- |
| 测试用例 | 预期值、等价类、断言是否能区分故障 | 夹具、数据、断言是否实际触发 | 用例适用条件、版本及预期是否同步 |
| 测试平台 | 环境、观测与隔离方案是否足够 | 加载对象、依赖、运行与收集链路 | 工具版本、配置、已知限制是否可追踪 |
| 被测对象 | 边界契约、状态、时序是否成立 | 首个偏离点、错误传播、可观察副作用 | 接口、构建或发布说明是否对应本次制品 |

## 可执行检查

Python 工作流的 `repair` 可声明 `repair_probe`。执行器在模型阶段之前核对已声明的失败退出码和实测失败标记，最终要求同一命令成功退出、有目标执行通过标记且旧失败标记消失。使用能定位目标用例的实际输出，例如测试框架的用例名及通过结果。见[工作流指南](../workflows/README.md)和[分页示例](../workflows/examples/pagination-task.json)。设计正确性、工具适格和发布包验证仍需相应证据。

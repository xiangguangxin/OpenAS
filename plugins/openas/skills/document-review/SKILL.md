# 文档评审

确认文档版本、目标读者、读者要完成的任务及评审范围。读取实际文档、相关 diff 和必要上下文，依据 [项目适配约定](../../references/project-context.md) 寻找对应源码、配置、测试、需求、设计或资料。默认只读；建议修订不等于获准改写文档或实现。

## 先确定事实基线

已有功能核对当前实现与适用版本；拟议设计核对已确认需求、有效决定和约束，不要求尚未实施的功能已经有源码。区分当前能力、历史结果、假设、计划与未决事项，检查是否把选配功能写成默认能力、把建议或静态推断写成实测结论。来源相互冲突时列出冲突及影响，不自行选择更方便的说法。

## 按读者任务核对

- **事实与接口**：功能、参数、默认值、路径、单位、错误语义、兼容要求及限制是否有依据；引用符号和示例是否对应实际版本。
- **操作完整性**：是否交代执行目录、依赖、必要配置、输入与预期结果；失败和恢复说明是否足以处理相关风险。只检查本次读者任务需要的内容，不按统一模板要求所有章节。
- **图文一致性**：组件名称、边界、箭头方向与关系类型是否和正文及事实基线一致；不能把依赖图当执行顺序。核心流程是否说明输入输出、状态变化和关键异常路径。文本核对不能冒充实际渲染或视觉检查。
- **可理解性与导航**：沿读者完成任务的顺序检查术语、前置知识、步骤、链接和跨文档引用；用具体歧义、遗漏步骤或无法完成的任务说明影响，不把措辞偏好、篇幅或个人排版习惯当作缺陷。

按需参考 [文档类型与核对点](../project-documentation/references/document-types.md)，不机械扩展评审范围。设计方案的可行性和实施就绪结论交给 [design-review](../design-review/SKILL.md)，实际代码缺陷交给 [requesting-code-review](../requesting-code-review/SKILL.md)；文档准确描述已有缺陷时，不把实现缺陷重复算作文档错误。

## 验证与证据

复用项目已有链接、文档构建和示例检查；先确认命令的实际副作用。只有在已有授权内且与评审有关时，才在隔离目录运行必要示例或渲染，保留命令、目录、退出码和结果。评审请求不自动授权外部写入、生产操作或依赖安装。缺环境、凭据或工具时标明具体未验证项，不把命令看起来正确当作运行通过；本地链接存在也不等于锚点、外部链接或使用路径有效。

## 发现与结论

沿用 [团队契约](../../references/team-contract.md) 的问题分级和宿主已有结论字段。每个发现包含稳定 ID、严重度、文档位置、对应事实来源、具体错误或读者反例、影响、建议修订及关闭证据。区分已确认问题、待确认项和可选建议；没有实质问题允许空 findings。

交付评审对象及版本、覆盖范围、问题列表、已执行检查、未验证项和 approve 或 needs_fix 结论。P0/P1 未解决不通过，P2 是否阻断依据原始验收和影响；缺少关键验证证据时不能声称对应操作已验证。复查保留原问题 ID，核对修订及关联内容。评审通过只表示本轮范围内未发现阻断文档问题，不表示代码或系统通过运行验收。

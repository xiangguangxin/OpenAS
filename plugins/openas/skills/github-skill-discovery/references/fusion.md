# 多来源技能融合

适用于用户已要求从多个技能提炼方法并生成新技能的任务。沿用入口的搜索、版本固定和审查要求；已有用户提供的候选也可以使用，明确是给定材料还是实时检索，不冒充完成外网搜索。

## 比较与提炼

先明确目标任务、产物、宿主和验收标准，再决定需要哪些来源。不设最低来源数量，不为凑数纳入重复或不适用的技能；单一来源足够时说明这是适配。

按能力而非按仓库罗列比较，例如需求澄清、任务组织、执行工具、质量检查和交付。对每个有价值的方法写清：解决什么问题、何时适用、需要什么输入与依赖、如何验证，以及在目标环境中保留还是替换。没有实际脚本、工具或证据支持的承诺不能继承。

区分处理方式：原样复制、翻译或改写、仅借鉴工作方法、独立实现。保留这种区别，不将改写或独立实现描述为自动免除来源义务。许可证不明、禁止本次修改或分发的候选排除并记录原因，不通过摘要再引入其内容。

## 冲突取舍

每个冲突形成一条可复核的决定：来源意见、目标约束、选择及理由、验证方法。常见冲突包括互斥工具链、不同输入输出格式、全局安装要求、付费服务、宿主专属命令和相反的验收标准。

依据客户的任务和实际环境选择一致的默认路线；只有存在真实使用场景时才保留可选分支。删除重复步骤、无依据的强制重试和无法迁移的宿主要求。涉及不同许可证的内容分别检查适用条款和组合后的交付条件，不能因为分别可用就假定组合可分发；无法解决时剔除相关输入或交付缺口说明。

## 编写新技能

在独立且不会被自动发现的目录中，以目标能力命名技能。重新组织简短的 `SKILL.md`：明确触发范围、必要决策、执行与验收；把只在特定模式下需要的细节放入 references。不要保留多个相互竞争的总入口，也不要把上游全部文档打包。

脚本只服务确定、可重复的实际工作；审查后复用允许使用的实现，或独立实现。宿主工具、依赖版本、凭据变量和可选服务按目标环境说明，不继承当前会话的隐含工具。若目标环境提供技能创建工具，可用它校验格式；不得将该工具作为客户必备依赖。

随新技能维护：

- `FUSION_SOURCES.json`：实际查阅日期、各来源仓库、技能路径、完整提交 SHA、固定链接和审查文件指纹；注明指纹针对原始字节还是规范化文本。每个来源记录采用项、弃用项及原因。
- 方法映射：每项采用的方法对应来源文件或章节、处理方式、目标文件或章节、依赖和验收方法。可以放在来源清单或独立 reference 中；不要只写“融合了三个来源”。
- 法律记录：保留适用的 LICENSE、版权和 NOTICE，标明改动与交付许可范围。新写代码与上游资源分别说明，不能用项目根许可证覆盖外部条款。
- 验证记录：命令、结果、产物路径、验证版本及未运行项。最终包记录文件清单和 SHA-256，排除记录自身，注明计算范围；后续修改后重新生成并验证。

这些是记录约定，现有 `import_skill.py` 不解析或验证 `FUSION_SOURCES.json`。可参考 `presentation-creation/FUSION_SOURCES.json` 和 `NOTICE.md` 的实际内容，但其字段不构成通用自动校验 schema。

## 验证、注册与维护

先检查 frontmatter、链接、资源完整性与依赖，再以隔离材料执行代表性任务和一个不应生成或不应触发的场景。重点验证融合后的交接：输出格式能否被下一步消费、工具替换是否可用、质量要求是否有实际检查。涉及输出文件时打开或渲染实际产物，而非只检查文件存在。

用目标任务的验收标准评估是否优于直接适配：解决了哪些原候选的缺口、是否增加了不必要依赖。不编造提升比例；没有行为验证时交付候选并注明未验证，不能标记客户端验收通过。

按用户授权将通过审查的产物注册到明确的技能目录。编入 OpenAS 源码时同步技能入口、插件版本、变更记录并运行仓库检查；不增加技能时不改变技能总数。已有目标不得覆盖，先比较差异并按既有迁移约定处理。宿主发现和实际调用分别记录；没有目标客户端时如实保留未验证状态。

交付新技能路径、核心取舍、来源及许可、依赖和真实验证结果。新生成技能的安装不授权提交或推送。后续更新逐个来源比较完整提交差异，重审受影响的方法、法律文件及依赖并重跑相关验证；不自动合并上游指令。

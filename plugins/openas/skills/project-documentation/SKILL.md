# 项目文档

先确认读者要完成的任务及用户指定文件。读取 [项目约定](../../references/project-context.md)、现有文档、相关源码和 CI，沿用项目语言、目录与风格。润色任务保留正确含义，不为改措辞重构整套文档。

尚无实现的新项目可以依据需求、调研和设计决策编写拟议设计文档，明确文档状态。需要从市场调研串起完整设计时，按 [完整流程与交付结构](../solution-design/references/research-to-design.md) 汇总实际产物；写作时保留未知与冲突，不擅自补出已经确定的架构。

## 选择内容

根据交付物按需读取 [文档类型与核对点](references/document-types.md)。先写读者最需要的结果和操作路径，再补必要原理；不强制每个文档包含全部章节。

编写设计文档时，在目标与范围之后先画一张总览架构图，再展开方案和组件细节。已有准确的图可以更新复用。图中标出系统边界、主要组件及它们之间的关系，并按边界、层次和职责合理布局；箭头说明是调用、数据流还是依赖，不把静态依赖画成执行顺序。需要精确控制组件、连线与文字布局时，可使用仓库的 [technical-diagrams](../technical-diagrams/SKILL.md) 技能绘制可维护的 SVG 矢量架构图，并嵌入文档。图后用简短文字说明整体如何工作、各组件负责什么，并沿着“输入来源 → 处理与传递 → 输出去向”描述数据流。写清关键步骤的输入、输出、状态变化，以及分支条件和失败、重试或结束状态；说明由谁处理异常。图和文字使用相同名称，读者不看图也应能理解主要逻辑。其他绘图方法也按该技能选择。

用短句和常用词解释“谁做什么、为什么这样连接”，首次出现的必要术语给出解释。只写对读者理解设计有用的细节；图难以承载的异常路径、约束和取舍在正文说明，不在图中堆满文字。

- 每项功能、参数、默认值和限制对应源码、配置、测试或可信资料。区分当前能力、可选依赖、实验特性和未来计划。
- 命令说明执行目录、前提、必要输入及预期结果。示例使用占位值，不暴露凭据，不将宿主临时路径写成通用路径。
- 接口说明包含输入输出、单位、错误和兼容行为；部署及运维说明覆盖配置、启动、健康检查、故障定位和适用的恢复方式。
- 其他图表也按 [technical-diagrams](../technical-diagrams/SKILL.md) 选择。链接优先项目内相对路径；对代码说明保留稳定的符号/路径及版本背景，避免大段复制易过时实现。

## 核对与交付

执行项目已有文档检查，核对相对链接、代码围栏、示例与参数。设计文档还要核对架构图中的组件、箭头方向与关系类型是否和正文、接口及实际设计一致，检查输入输出、状态变化和异常分支是否交代清楚，并确认不熟悉项目的读者能读懂。按风险在隔离目录验证安装或使用示例；有破坏性、外部写入或凭据需求的命令不得仅为验证文档就执行。无法运行时说明具体未验证项，不能声称示例已跑通。

保持修改与请求有关，检查 diff 和图文一致性。交付变更位置、主要内容及验证范围。需要角色协作时可由 tech-writer 编写、主执行者或 verifier 执行检查；普通文档修改不要求完整开发团队。

独立文档评审使用 [document-review](../document-review/SKILL.md)，可由 red-team 承担；编写中的自检不冒充独立评审，只读评审不自动修改文档。
